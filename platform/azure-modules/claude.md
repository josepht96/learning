# Terraform Modules Monorepo: Agent Instructions

## Goal

This repository contains many reusable Terraform modules in a single repo. Each module is **versioned and released independently**, so a consumer can use `vpc` at `1.2.3` and `rds` at `1.2.4` at the same time.

Before starting implementation, confirm with the user:

- Git host (GitHub or GitLab) and CI platform (GitHub Actions or GitLab CI).
- Repository URL (used in consumer examples).
- Initial list of modules to create.

## Repository Layout

```
terraform-modules/
├── modules/
│   └── <module-name>/
│       ├── main.tf
│       ├── variables.tf
│       ├── outputs.tf
│       ├── versions.tf
│       ├── VERSION            # single line, e.g. 1.2.3
│       ├── CHANGELOG.md
│       ├── README.md          # generated by terraform-docs
│       ├── examples/
│       │   └── basic/         # minimal working usage
│       └── tests/
│           └── basic.tftest.hcl
├── scripts/
│   ├── changed-modules.sh     # lists module dirs changed vs. base ref
│   ├── check-version-bump.sh  # PR check: changed modules must bump VERSION
│   └── release.sh             # main: tag modules whose VERSION changed
├── .tflint.hcl
├── .terraform-docs.yml
└── CLAUDE.md
```

Module directory names are lowercase kebab-case, unique, and flat under `modules/` (no nesting).

## Module Standards

Every module MUST:

1. Declare `required_version` and `required_providers` in `versions.tf` using **minimum** constraints (e.g. `aws = { source = "hashicorp/aws", version = ">= 5.0" }`). Never pin exact provider versions in a module.
2. **Not** contain `provider` blocks. Consumers configure and pass providers.
3. Give every variable a `description` and `type`. Use `validation` blocks for constrained inputs.
4. Give every output a `description`.
5. Include at least one working example under `examples/` and one `terraform test` file under `tests/`.
6. Have a README generated by terraform-docs, including a usage snippet with the correct `source` and tag format.

Modules MUST NOT reference sibling modules by relative path (e.g. `source = "../vpc"`). This couples releases across modules. If composition is needed, either:

- compose in the consumer's root module (preferred), or
- reference the sibling by git source pinned to a released tag, exactly as an external consumer would.

## Versioning

### Scheme

Semantic versioning per module. The `VERSION` file in each module is the source of truth.

- **MAJOR:** any change that breaks existing consumer code or state:
  - removing or renaming a variable or output
  - making an optional variable required
  - changing a default in a way that changes deployed infrastructure
  - raising the minimum provider major version
  - changing a resource address (rename, adding `count`/`for_each`) **without** a `moved` block
- **MINOR:** new optional variables, new outputs, new opt-in features, refactors covered by `moved` blocks.
- **PATCH:** fixes that do not change the interface and do not force resource replacement.

When refactoring resource addresses, ALWAYS add `moved` blocks so consumers get an in-place state move instead of destroy/recreate.

New modules start at `0.1.0`. Promote to `1.0.0` when the interface is considered stable.

### Tag format

```
<module-name>/v<MAJOR>.<MINOR>.<PATCH>
```

Examples: `vpc/v1.2.3`, `rds/v1.2.4`. Tags are immutable: never move or delete a published tag.

### Changelog

Every version bump adds an entry at the top of the module's `CHANGELOG.md`:

```markdown
## 1.2.4 - YYYY-MM-DD
### Fixed
- Description of change.
```

MAJOR releases include an **Upgrade notes** section describing required consumer changes.

## CI: Pull Requests

Run only for modules changed in the PR (`scripts/changed-modules.sh` compares against the base branch). Changes outside `modules/` (CI config, scripts, docs) do not require a version bump.

For each changed module, run:

1. `terraform fmt -check -recursive`
2. `terraform init -backend=false` and `terraform validate` (module and each example)
3. `tflint`
4. Security scan (`checkov` or `trivy config`)
5. `terraform test`
6. terraform-docs check: README is up to date
7. `scripts/check-version-bump.sh`, which fails if:
   - module files changed but `VERSION` did not change
   - the new `VERSION` is not greater than the previous one
   - the tag `<module>/v<VERSION>` already exists
   - `CHANGELOG.md` has no entry for the new version

## CI: Release on Merge to Main

`scripts/release.sh`:

1. Find modules whose `VERSION` file changed in the merge.
2. For each, create and push an annotated tag `<module>/v<VERSION>` at the merge commit, with the changelog entry as the tag message.
3. Skip (do not fail) if the tag already exists at the same commit; fail if it exists at a different commit.
4. Optionally create a GitHub/GitLab release per tag with the changelog entry.

The script must be idempotent and safe to re-run.

## Consumer Usage

Document this in the root README and in each module README.

```hcl
module "vpc" {
  source = "git::https://<git-host>/<org>/terraform-modules.git//modules/vpc?ref=vpc/v1.2.3"
}

module "rds" {
  source = "git::https://<git-host>/<org>/terraform-modules.git//modules/rds?ref=rds/v1.2.4"
}
```

Notes for consumers:

- The double slash (`//`) separates the repo URL from the module subdirectory.
- Git sources do not support the `version` argument; the `ref` is the version.
- Module versions are not recorded in `.terraform.lock.hcl` (it locks providers only), so always pin an exact tag.
- Run `terraform init -upgrade` after changing a `ref`.
- For automated upgrade PRs (Renovate), configure version extraction per module tag prefix, e.g. `^vpc/v(?<version>.+)$`.

## Rules for the Agent

- Make one logical change per PR where possible. If a PR touches multiple modules, bump each changed module's `VERSION` and `CHANGELOG.md` independently.
- Classify every change as MAJOR, MINOR, or PATCH using the rules above, and state the classification in the PR description.
- Never edit a module without running its tests and `terraform validate` locally.
- Never create, move, or delete tags manually. Tags are created only by the release pipeline.
- Do not introduce relative-path references between modules.
- Do not add `provider` blocks or exact provider pins to modules.
- Keep shared tooling (scripts, CI config) changes in separate PRs from module changes.

## Acceptance Criteria (initial setup)

- [ ] Repository layout matches this document.
- [ ] At least two example modules exist, each with `VERSION`, `CHANGELOG.md`, example, test, and generated README.
- [ ] PR pipeline runs checks only for changed modules and enforces the version bump rules.
- [ ] Release pipeline creates `<module>/v<VERSION>` tags on merge and is idempotent.
- [ ] A sample consumer root module (outside `modules/`, e.g. `consumer-example/`) successfully uses two modules at different versions via git refs, and `terraform init` and `terraform validate` pass.
